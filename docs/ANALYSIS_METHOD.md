# 分析方法论：拐点定义、外推、预算分配

本文说明 `autosafe/metrics.py` 与 `autosafe/budget.py` 里每个判定背后的**为什么**，
以及这些方法的适用边界。所有数字可在 `results/analysis.json` 中复核。

---

## 1. 为什么用"每 10 万 token 修复数"作为边际收益

三个候选口径的对比：

| 口径 | 公式 | 问题 |
|---|---|---|
| 每轮修复数 | `round_fixed` | 单轮 token 会随上下文膨胀上涨，用轮次做分母会**系统性低估**后期成本 |
| 每轮修复数 / 该轮 token | `round_fixed / round_tokens` | 无量纲，但不同模型的 token 计价不同，难以横向比较 |
| **每 10 万 token 修复数** | `round_fixed / round_tokens × 100_000` | ✅ 以 token 为统一货币，可跨任务类型、跨模型、跨预算规模比较 |

选第三个。阈值 **0.1**（即"再花 10 万 token 只能多修不到 0.1 个漏洞"）是用户给定的
业务判据——它把"值不值得继续"翻译成一个可测的数字，而不是主观的"感觉差不多了"。

**这个阈值的含义**：10 万 token 大致相当于一次完整的中等规模代码库审计（约 25 个
函数的上下文）。如果花掉这么多 token 却修不出哪怕 0.1 个漏洞（即平均要花 100 万 token
才能多修 1 个），从工程角度就不划算了。

## 2. 拐点判据：三重定义，主判据是 A

真实曲线的形状比教科书复杂：本项目实测的边际序列是

```
25.96 → 7.21 → 6.85 → 9.26 → 1.78 → 0.00 → 0.00 → 1.66
```

注意两个反直觉之处：
- **第 4 轮反弹**（9.26 > 6.85）：某个难修的缺陷在前几轮铺垫后终于被修好
- **第 8 轮反弹**（1.66 > 0）：长尾缺陷直到很晚才暴露

如果只用"首次低于阈值"（第 6 轮），结论看似没问题；但如果某条曲线在**第 2 轮**偶然
低于阈值又在第 3 轮反弹，只看"首次"就会把拐点误判到第 2 轮。

### 判据 A（主判据）：持续低于阈值，允许尾部孤立反弹

拐点 = 第一个轮次 r，满足：

1. **第 r 轮本身低于阈值**（否则拐点无意义）
2. 从 r 到末尾，高于阈值的轮次数 ≤ `max_isolated_rebounds`（默认 **1**）
3. 该孤立反弹**不能紧邻拐点**（r+1），且**反弹之后必须还有低值轮次**
   （特例：反弹落在最后一轮，属于典型长尾，仍算孤立）

条件 3 是关键。它排除两类伪拐点：
- "刚跌破阈值就立刻反弹" → 说明还没真正趋零
- "最后几轮连续高收益" → 说明仍在持续产出，不叫拐点

### 判据 B（对照）：尾部平均

从 r 到末尾的 `总增量修复 / 总增量 token < 阈值`。
这是"在 r 之后每额外 10 万 token 多修复不到 X 个"的**字面实现**，天然抗单点噪声。
缺点：尾部样本少时会被一两次反弹稀释（本轮实测 `tail_avg_knee_round = None`，
因为第 8 轮那一次 1.66 的反弹把尾部平均抬过了阈值）。故作为对照而非主判据。

### 判据 C（无标度对照）：相对阈值

边际收益跌破**首轮的 10%**。不依赖绝对 token 规模，
用于验证"结论不是阈值尺度造成的假象"。本轮实测指向第 5 轮，与 A 相差 1 轮。

### 三重判据的一致性检验

本轮真实数据的三个结果：

| 判据 | 拐点 | 说明 |
|---|---|---|
| A 持续低于（主） | **第 6 轮** | 第 6、7 轮严格为 0，第 8 轮一次孤立反弹 |
| B 尾部平均 | 未达 | 第 8 轮反弹稀释了尾部样本 |
| C 相对阈值 | 第 5 轮 | 首轮 25.96 的 10% = 2.60，第 5 轮 1.78 已低于 |
| 阈值敏感性 0.05/0.1/0.2 | **均为第 6 轮** | 结论对阈值选择不敏感 |

三者落在第 5–6 轮，**结论稳健**。报告中采用 A 的结论（第 6 轮）并注明保守性。

## 3. 未观测到穿越时的处理：log-linear 外推

若整个观测窗口（8 轮）内都没跌到阈值以下，但趋势显著下降，用对
`(round, log(marginal + ε))` 的线性回归外推穿越点：

```
log(marginal) = a + b·round
round_cross   = (log(threshold) − a) / b      当且仅当 b < 0 且 R² ≥ 0.6
```

**三条纪律**：
1. 外推结果标记 `method="loglinear_extrapolation"`、`observed=False`，**绝不伪装成观测值**
2. 外推值 clamp 到 `[1, 20]` 轮，防止荒谬外推
3. 趋势不显著（b ≥ 0 或 R² < 0.6）时明确返回 `not_reached`，不硬凑答案

本轮真实数据 8 轮内已观测到穿越，未触发外推分支——这是最理想的情况。

## 4. 累计曲线的聚合口径（一个真实 bug 的教训）

初版 `aggregate_curve` 只对"跑到第 r 轮的任务"求和。任务提前收敛后，总和会**下降**，
于是产生负的边际收益（实测出现过 −380.95），`log(负数)` 直接让外推崩溃。

**修正后的口径**：第 r 轮的值 = 每个任务跑到 `min(r, 该任务实际轮数)` 时的累计值之和，
即"把 N 个任务都审到第 r 轮，提前收敛的沿用其最终值"。

理由：**已花的 token 不会退回来**。累计曲线必须单调不减，这是"累计"二字的定义要求。
修正后实测累计曲线严格单调，边际收益全部 ≥ 0。

这个 bug 值得记录，因为它揭示了一个更普遍的道理：**用"存活任务"做分母会自动产生
"后期更便宜"的假象**（存活的任务往往是难修的），足以让整个边际分析反向。

## 5. 建议迭代深度：为什么按任务类型分化

`recommend_depth()` 的输出逻辑：
- 观测到拐点 → `recommended_depth = ceil(knee_round)`
- 未观测到 → `min(外推拐点, 达到 90% 收益所需轮次)`
- 一律 clamp 到 `[1, max_rounds]`

本轮真实结果（差异显著，正是"按类型定深度"的价值所在）：

| 任务类型 | 建议深度 | 拐点 | 修复单价 (token/个) |
|---|---|---|---|
| randomness | 6 | 6.0 | 24,384 |
| authz | 5 | 5.0 | 12,136 |
| path_traversal | 4 | 4.0 | 5,582 |
| crypto | 3 | 3.0 | 4,614 |
| secrets | 3 | 3.0 | 4,255 |
| config | 2 | 2.0 | 3,953 |
| deserialization | 2 | 2.0 | 3,847 |
| injection | 2 | 2.0 | 3,126 |
| web | 2 | 2.0 | 26,952 |

**解释**：injection/deserialization 的缺陷有明确的代码特征（危险 sink），bandit 一轮全报，
第 2 轮后无新收益。randomness/authz 属于语义类缺陷——工具看不见，只能靠 LLM 反复提示
逐步逼近，所以要 5–6 轮。web 类型建议深度虽只有 2，但**修复单价高达 26,952**
（是 injection 的 8.6 倍）：说明它的缺陷一旦被发现就很难真正修好，属于"发现便宜、修复昂贵"
的另一类长尾。**这正是"建议深度"必须和"修复单价"一起看的原因**——深度短不等于便宜。

## 6. 预算分配：三种策略与贪心近似比

### 问题形式化

给定预算 B、任务集合 T、每任务最大轮次 K，选择分配 `{t: k_t}` 最大化
`Σ benefit(t, k_t)`，约束 `Σ cost(t, k_t) ≤ B`，且 `k_t` 必须**前缀连续**
（跑第 3 轮必须先跑第 1、2 轮，因为第 2 轮的发现是第 3 轮修复的前提）。

这是**带前缀约束的多选择背包（multiple-choice knapsack with precedence）**。

### 三种策略

| 策略 | 做法 | 定位 |
|---|---|---|
| **breadth** | 所有任务统一跑 k 轮，取预算允许的最大 k | 均匀覆盖，不看边际 |
| **depth** | 少数任务跑到 K 轮，预算够则继续新增整任务 | 集中加固高风险资产 |
| **adaptive** | ① 每任务先跑 1 轮做全覆盖探查；② 剩余预算按"下一轮边际修复密度"贪心加深 | 本文推荐 |

### adaptive 的两个设计要点

**要点 1：为什么需要"探查地板"**
纯贪心只看已知边际密度，会跳过那些**首轮没修出东西**的任务（密度=0），
从而永久漏掉可能在第二轮才暴露的长尾缺陷。真实审计不会因为"第一次扫描没发现"
就放弃一个资产。加一轮全覆盖探查后，adaptive 的投影收益从 32 提升到 46（+44%）。

**要点 2：为什么要允许"跨过零收益轮"**
很多任务第 1→2 轮边际为 0，若严格要求"密度 > 0"才加深，会在探查后立刻停止，
退化成"只跑 1 轮"。修正为**前瞻密度**：若下一轮为 0 但后续轮次有收益，
按 `(后续收益 / 从当前到该轮总成本) × 0.5` 折价计分（折价体现"要先买无用轮次"的代价）。
这一修正把 adaptive 的平均深度从 1.24 提到 2.36，收益从 35 提到 46。

### 贪心近似比

前缀约束背包是 NP-hard，贪心不保证全局最优。近似比界：

设所有"可购买轮次"的边际密度落在 `[d_min, d_max]`，则贪心解 `G` 与最优解 `OPT` 满足
`G ≥ OPT / (d_max / d_min)`（每步取最大密度，最坏情况是剩余预算装不下任何高密度轮次）。
实际数据里 `d_max/d_min` 因大量 0 密度轮次而趋于无穷，所以**该理论界很松**。

更有意义的验证是**与其他策略的实证对比**（本轮真实执行，预算 40 万）：

| 策略 | 覆盖 | 平均深度 | 实际 token | 实际修复 | 修复单价 | vs breadth |
|---|---|---|---|---|---|---|
| breadth | 25 | 3.00 | 260,110 | 38 | 6,845 | 基准 |
| depth | 13 | 8.00 | 175,693 | 33 | 5,324 | −13.2% |
| **adaptive** | **25** | **2.36** | **245,699** | **46** | **5,341** | **+21.1%** |

adaptive 同时赢在"修得多"（+21%）和"花得少"（−5.6% vs breadth）。
depth 修得最少却也花了不少——集中深挖的代价是放弃了 12 个任务的全部漏洞。

### 投影 vs 真实执行

三种策略的 `projected_fixed`（用主实验观测曲线离线投影）与 `actual_fixed`
（按方案真实跑管线）**完全一致**（38 / 33 / 46），投影误差为 0。

这说明：**只要已有基线实验的逐轮曲线，预算规划可以完全离线完成**，
不必为每个候选方案都真实跑一遍。对真实工程的意义是——先花一次基线成本，
之后所有预算决策都可以在秒级内算出，这在 token 计费场景下是直接的省钱能力。

## 7. 方法局限（必须诚实声明）

1. **模拟 provider**：LLM 输出长度与发现/修复决策是确定性建模的，不是真实 API 调用。
   token 的**绝对量级**与曲线**形状**都来自该模型；换真实模型后绝对数会变。
   但记账口径与分析方法（比值、拐点、预算投影）可直接迁移——见 `docs/TOKEN_CALIBRATION.md`。
2. **字符级 token 估算**：误差约 ±8%。因为拐点用**比值**判定，分子分母同比例缩放
   不影响结论；但"累计 token"的绝对值有该量级的不确定性。
3. **手工构造的任务库**：25 个任务、76 个缺陷，规模远小于真实代码库。
   结论的**方向性**（边际递减存在、深度不如广度、bandit 通道更便宜）应可迁移，
   但具体轮次数值（第 6 轮、2–6 轮深度）依赖任务规模与代码长度，**不可直接外推**。
4. **真实工具有效性边界**：bandit 与 fuzz 是真实执行，但 bandit 只能覆盖有静态特征的
   缺陷；语义类缺陷仍需 LLM 推理，这部分是建模的。所以 `channel_breakdown` 里
   bandit 的数字最可信，semantic 的数字参考价值最低。
5. **单一 seed 的主结论**：主实验用 seed=7。灵敏度分析（strong/baseline/weak × 3 seeds）
   用于检验结论对模型能力的稳健性，见 `results/sensitivity.json`。
