## 一、项目一句话（简历条目用）

**AutoSafe-Audit：多 Agent 代码安全审计的 token 边际收益分析**（个人项目，2026）

> 在 25 个漏洞任务上，迭代到**第 7 轮**后每 10 万 token 修复漏洞数跌破 0.1；
> 在同样 40 万 token 预算下，按边际收益贪心分配比广度铺开**多修 17.0%（55 vs 46 个）**，
> 而"少数任务挖到底"的策略**少修 27.7%**，是明确的负收益。

**短版（一行，放在技能栏或摘要里）**

> 用真实 bandit + 子进程 fuzz 做判定的三 Agent 安全审计实验台，量化出「迭代深度的 token 拐点」，
> 并给出分类型的建议深度与预算分配方案。

## 二、STAR 结构

### Situation（背景）

AutoSafeCoder 等研究工作报告了「多 Agent 迭代能让漏洞减少 13%」这类结果。但这类报告有一个
共同的缺口：**没人算这笔账的成本**。

安全团队真实面对的问题是「预算有限，要不要再多跑一轮审计」——而论文只告诉你「更深的迭代
能修更多漏洞」，却不告诉你**第几轮之后每一分钱都是浪费的**。在真实的安全工程里，
这个判断比「提升 13%」更有决策价值：它决定了预算该切在哪里。

### Task（任务）

构建一个可复现的实验台，回答三个问题：

1. 多 Agent 安全审计的**边际收益**随迭代轮次如何衰减？拐点在哪？
2. 不同漏洞类型（注入 / 鉴权 / 密码学 / 反序列化 …）的**建议迭代深度**是否相同？
3. 在固定 token 预算下，**广度铺开**、**少数深挖**、**按边际收益贪心**，哪种花法更划算？

约束：无外网 API key、不可联网、单机可复现。

### Action（行动）

1. **搭三 Agent 迭代管线**：Coding Agent（写实现/打补丁）→ Static Analyzer Agent
   （真实调用 bandit CLI + 语义复核）→ Fuzzing Agent（真实子进程跑 harness 收集 marker），
   每轮把未修好的缺陷喂回 Coding Agent 形成闭环，最多 8 轮。

2. **把"判定权"从模型手里拿走**：这是整个项目可信的基础。是否发现漏洞，由 **bandit 真的报出
   对应 `test_id` 且行号落在 ±5 行内**决定；是否修好，由**重新跑 bandit + fuzz + 正则三重验证**
   决定。模型的输出只当作"候选"，不当作"结论"。

3. **逐轮精确记账**：每个 Agent 每次调用的 `tokens_in + tokens_out` 都记进 `RoundRecord`，
   同时记 `defects_found / fixed / duplicate_findings / noise_findings`。
   定义核心指标 **「每 10 万 token 修复漏洞数」= 当轮修复数 / 当轮 token × 100,000**。

4. **拐点检测**：在聚合曲线上找「边际收益持续跌破 0.1/10万 token」的轮次；
   若观测窗口内未跌破，用**对数线性外推**给出插值轮次并标注方法（`observed` /
   `loglinear_extrapolation` / `not_reached`）——**不假装观测到了没观测到的东西**。

5. **分类型建议深度**：对 9 个 family 各自算拐点、90% 收益轮次、修复单价，
   用 `recommend_depth()` 输出带中文 `rationale` 的深度建议，而不是给一个全局的"跑 5 轮"。

6. **预算分配对比**：把「每任务分配几轮」建模成**前缀约束的背包问题**（要跑第 k 轮必须先跑
   k−1 轮），用观测曲线投影三种策略（breadth / depth / adaptive），
   对比总 token、总修复数、每修复 token。

7. **可视化与报告**：5 张图（累计曲线 / 边际收益双面板 / 分类型深度 / 预算对比 / 任务×轮次热力图），
   全部中文字体、DPI 180，每张图自带「读图要点」；报告由脚本从 JSON 自动生成，数字不做人工修饰。

### Result（结果）

| 指标 | 结果 |
| --- | --- |
| 任务规模 | 25 个任务 / 9 个类型 / **80** 个真实缺陷 |
| 总消耗 | **567,592** token，修复 **57** 个（修复率 **71.2%**），平均 4.76 轮 |
| 拐点 | **第 7 轮**，累计约 **51.4 万** token 时边际收益跌破 0.1 |
| 边际收益序列 | 26.57 → 8.80 → 7.97 → 8.97 → 3.71 → 1.91 → **0.00** → 1.90 |
| 建议深度 | **2–6 轮**（按类型分化：随机性 6 轮、鉴权 5 轮、注入类 4 轮、反序列化 2 轮） |
| 平均成本 | 每修复 1 个漏洞 **9,958** token |
| 预算策略 | adaptive **55 个 / 31.7 万**；breadth 47 个 / 29.0 万；depth 34 个 / 18.6 万 |
| 策略差异 | adaptive 比 breadth **多修 17.0%**（多花 16% token）；depth 比 breadth **少修 27.7%** |
| 通道差异 | fuzz 修复率 **81.8%**（最高）/ 34,383 token；semantic 76.2% / 38,288；bandit 62.2%（最低）/ 28,522（最便宜） |
| 工具盲区 | **1 个缺陷从未被任何通道发现**（深挖也挖不出来） |
| 投影精度 | 三种策略的投影修复数与真实执行**完全一致（误差 0%）** |

**最有价值的四条结论**：

1. **第 7 轮边际严格为 0（纯烧钱）**，第 8 轮因一个长尾缺陷被修好而反弹到 1.90。
   阈值敏感性 0.05 / 0.1 / 0.2 **全部指向第 7 轮**，结论对阈值不敏感。
   **深挖偶尔有惊喜，但期望值极低。**
2. **"检出的便宜"不等于"修好的便宜"**：bandit 修复单价最低（28,522）但修复率也最低（62.2%），
   因为静态告警混有噪声、Agent 要额外花成本甄别；fuzz 检出的缺陷带可复现的失败用例，
   修复率最高（81.8%）。→ 静态做筛查、fuzz 做确认，两者角色不同。
3. **"少数任务挖到底"是三种预算策略里最差的**：depth 少修 27.7%，还放弃了 14 个任务。
   自适应（全覆盖 + 按边际加深）用 +16% 的 token 换 +17.0% 的修复，
   多出的每 1 个修复只花约 3,302 token（远低于平均 9,958），**边际性价比为正**。
4. **「工具盲区」真实存在**：80 个缺陷里有 1 个从未被任何通道发现。
   → 「提高迭代深度」和「提高检出能力」是两个不同问题：前者有明确拐点，后者才是修复率上限的杠杆。

## 三、技术亮点（每条一句话，突出"工程判断"而非"调模型"）

1. **把"要不要继续迭代"从经验判断变成可测量指标**：定义「每 10 万 token 修复数」，
   用曲线拐点决定预算切点，替代「凭感觉定跑 5 轮」。

2. **判定权交给真实工具，不给模型自评的机会**：漏洞是否发现由 bandit 的 `test_id` + 行号
   匹配决定，是否修好由重新扫描三重验证——这是所有成本数字可信的前提。

3. **诚实处理"没观测到"的情况**：拐点未在窗口内出现时，明确标注是**对数线性外推**而非观测值，
   并在报告里给出可外推/不可外推的边界。

4. **把预算分配建模成前缀约束背包**：因为"跑第 k 轮"依赖"跑过 k−1 轮"，
   标准背包不适用；用按边际收益的贪心近似，并用真实观测曲线投影三种策略做对比。

5. **分类型而不是一刀切**：9 个 family 的收益衰减速度不同，注入类值得深挖、
   配置类漏洞 1–2 轮就够——建议深度是"按单价决定"，不是全局常数。

6. **全链路可复现**：所有随机性来自显式 `random.Random(seed)`，同 seed 重跑结果逐字节一致；
   报告与图表由脚本从 JSON 生成，数字不可手工修饰。

7. **图表也做正确性校验，不只是"画得好看"**：所有图表均经"数据不变式自动校验 + 人工目视"
   双重检查——**累计曲线强制单调不减、0 值不允许用对数轴表示、外推拐点必须与实测拐点视觉区分**。
   因为一张会让人误读的图比没有图更糟：它会让人以为自己看懂了。

## 四、面试可能被追问的 5 个问题 + 参考答案

### Q1：你怎么定义"拐点"？为什么是 0.1？

**定义**：拐点是「**边际收益持续跌破阈值**」的那个轮次。边际收益 = 当轮修复数 / 当轮 token
× 100,000，即「每烧 10 万 token 能买到几个修复」。

**为什么是 0.1**：0.1 个/10 万 token 意味着**修一个漏洞要烧 100 万 token**——这个量级下，
继续迭代的工程意义已经很小了。但更重要的是：**阈值本身是人为选的，所以必须做敏感性分析**。
我在 `analysis.sensitivity` 里同时给了 0.05 / 0.1 / 0.2 三个阈值下的拐点，
报告里也写明了换阈值拐点会移动。

**技术上怎么做的**：在聚合曲线上顺序扫描，找到第一个「边际收益 < 阈值」的轮次；
若整个观测窗口内都没跌破，就用**对数线性回归**（边际收益通常呈指数衰减）外推，
给出 `interpolated_round`，并把 `method` 标成 `loglinear_extrapolation` ——
**绝不把外推值伪装成观测值**。

### Q2：为什么模拟 LLM 还能得出有效结论？

因为**这个项目的结论不依赖"模型有多聪明"，而依赖"成本-收益的结构"**。

我建模的是三个真实世界效应，它们才是边际收益递减的成因：
1. **先易后难**：高严重度、低 subtlety 的缺陷优先进入 triage，剩下的越来越难；
2. **假补丁复发**：Agent 会用"看起来合理但无效"的补丁，下一轮被重新报告，token 花在同一个洞上；
3. **上下文膨胀**：历史 findings 进入 prompt，单轮 token 随轮次上升。

这三条只要成立，**拐点必然出现**——具体在第几轮取决于模型能力，但"存在拐点"和
"应该按拐点切预算"这两个结论是结构性的。**而且关键的判定环节全部是真的**：
bandit 是真的在扫，fuzz 是真的在子进程里跑，修复验证是真的在重扫。
模拟的只有"模型输出的 token 长度分布"。

**边界我也写清楚了**：绝对数值（拐点第几轮、每洞多少 token）不可外推到真实商业模型；
可迁移的是方向性结论。换真实 provider 只需设 `AUTOSAFE_LLM=litellm`，管线与记账口径不变。

### Q3：贪心背包的近似比是多少？

**先说为什么不是标准背包**：这里的问题是「每个任务分配跑几轮」，而"跑第 k 轮"依赖
"跑过第 k−1 轮"，所以每个任务的选项集合是**前缀**（0,1,2,...,8 轮），
这是一个**多选择背包（multiple-choice knapsack）/ 前缀约束背包**，仍是 NP-hard。

**贪心的近似比**：对**可分离、边际收益递减**（凹）的目标函数 + 前缀约束，
按「每 token 边际收益」从高到低贪心填充，是**1/2 近似**（标准背包贪心的经典结果：
取贪心解与"单个最优物品"中的较优者，可得 1/2 保证）。
如果每轮的边际收益序列本身是递减的（我的数据里成立），实际表现通常远好于 1/2。

**我没有声称最优**：报告里写的是"投影"，且 `compare()` 是用**真实观测曲线**投影三种方案，
不是解一个松弛后的连续优化。要最优可以上 DP（预算离散化），但那会把"预算"这个连续量
变成网格，反而引入伪精度——对"广度 vs 深度 vs 自适应哪个方向更好"这个问题，
1/2 近似的贪心已经足够给出可靠的**排序**结论。

### Q4：怎么证明结论不是过拟合？

四个层面：

1. **不调参**：拐点阈值、轮次上限、Agent profile 都是**先验设定**（对齐 AutoSafeCoder 的
   8 轮设置），没有为了让曲线好看而调过。`profile` 有 strong / baseline / weak 三档，
   主实验用 baseline，另外两档用于敏感性检查——**换档位后"存在拐点、深度应分类型"的排序稳定**。

2. **判定不依赖模型**：发现/修复的判定全部由 bandit + fuzz + 正则完成，
   不存在"模型说修好了就算修好"的自我循环。这消除了最大的一类过拟合来源。

3. **多阈值敏感性**：`analysis.sensitivity` 给了 0.05 / 0.1 / 0.2 三档，
   报告里明确写"换阈值拐点会移动"——不藏这个事实。

4. **诚实标注边界**：报告第 6 节把"任务数 25 偏少、每个 family 只有 1–5 个任务、
   单 seed 未做置信区间、token 估算器未用真实分词器校准"全部列为已知弱点。
   **一个不敢列弱点的实验，其结论才可疑。**

### Q5：这个项目如果用在真实代码库上，最大的坑是什么？

三个，按严重程度：

1. **上下文长度**：真实仓库的单个文件可能就超过这里的整个任务（≤70 行）。
   跨文件依赖、调用图、构建配置都会让 prompt 爆炸，"每修复 token"的绝对值会完全变形。
   这里测出 **9,958** token/洞（平均），真实项目里可能差一到两个数量级。

2. **真阳性率**：bandit 在真实代码库上的误报率很高（这里 `noise_findings` 已经在建模，
   但真实噪声分布更复杂）。误报会吃掉 triage 容量，让"发现"的成本结构完全不同。

3. **验证的代价**：这里"修好"可以用正则 + 重扫快速验证。真实项目里验证一个鉴权修复
   可能需要起服务、跑集成测试、人工审计——**验证成本可能超过生成成本**，
   这会进一步把拐点前移（更早就不划算）。

**所以我的结论只到"方向"这一层**：真实项目里也应该按边际收益切预算，
但那个点必须用**你自己项目的观测曲线**去测，不能抄我的数字。

## 六、一分钟口述版（面试自我介绍用）

> 我做了一个叫 AutoSafe-Audit 的项目，出发点是一个我觉得被忽略的问题：
> 多 Agent 安全审计的论文都在说"迭代能让漏洞减少 13%"，但没人算这笔账花多少 token。
>
> 我搭了个三 Agent 的迭代管线，关键设计是**判定权不给模型**——漏洞有没有被发现，
> 由真实 bandit 的告警和行号匹配决定；有没有修好，由重新扫描三重验证决定。
> 然后我逐轮记账每个 Agent 的 token，定义了「每 10 万 token 修复数」这个指标。
>
> 结果发现曲线有明显的拐点：**第 7 轮之后**，每 10 万 token 只能换来不到 0.1 个修复；
> 第 7 轮本身边际严格为 0（纯烧钱），第 8 轮只有一次孤立反弹。
> 我还发现不同漏洞类型的深度应该不一样（随机性 6 轮、反序列化 2 轮），
> 并且把预算分配做成了前缀约束的背包问题：**同样 40 万 token 预算下，
> 自适应策略比广度铺开多修 17.0%，而"少数任务挖到底"反而少修 27.7%**。
>
> 有个细节我很喜欢：80 个缺陷里有 **1 个从未被任何通道发现**——这说明
> 「迭代更深」和「检出力更强」是两个不同的问题，前者有明确拐点，后者才是修复率的上限。
>
> 这个项目我最想展示的不是"我会调模型"，而是**在安全工程场景里做成本-收益判断**的能力——
> 知道什么时候该停，比知道怎么跑更重要。
