## 三、STAR 完整版（用于详细项目经历，约 200 字）

**背景**：AutoSafeCoder 等研究证明多 Agent 迭代审计能把漏洞减少约 13%，但没有人回答第二个问题——
**这个提升花了多少 token？迭代到第几轮之后继续审计不再划算？**

**做法**：
- 搭建三 Agent 迭代管线：Coding Agent 生成/修复代码，Static Analyzer（真实调用 `bandit` CLI）与
  Fuzzing Agent（真实子进程执行恶意输入）负责发现，修复后**重新扫描验证**——判定不交给模型自评。
- 对每一轮精确记账三个 Agent 的输入+输出 token，同时记录累计 token、累计修复；
  用「每 10 万 token 修复漏洞数」作为边际收益指标。
- 在 25 个手工构造的漏洞任务（80 个真实缺陷，覆盖 CWE-89/78/22/502/327/798/862/330 等 9 类）上
  跑 25×8 轮，定位边际收益拐点，并按漏洞类型给出分化建议深度。
- 设计三种预算分配策略（广度优先 / 深度优先 / 按边际收益自适应贪心），用**真实执行**对比。

**结果**：
- 边际收益从首轮 26.60 衰减到第 7 轮的 **0.00 个/10 万 token**，**拐点在第 7 轮**；
  阈值 0.05/0.1/0.2 三档均指向同一轮次，结论对阈值不敏感。
- 全量 567,592 token、修复 57/80（71.2%），平均 **9,958 token/个**。
- **"深度迭代"是最差策略**：只修 33 个（比广度少 27.7%），还放弃了 14 个任务；
  "自适应"比广度**多修 17.0%**，且增量部分的边际性价比仍为正（每多修 1 个仅 ~3,601 token）。
- 敏感性分析（3 档模型能力 × 3 个 seed，共 9 次独立运行）显示拐点稳定落在第 5–8 轮，
  且**模型越弱拐点越晚、越贵**：弱模型每修复成本是强模型的 2.0 倍。

## 六、面试可能追问的问题（附参考答案）

### Q1：你怎么定义"拐点"？为什么是 0.1？

**答**：拐点定义为「边际收益持续低于阈值的最早轮次」，边际收益 = 该轮新增修复数 ÷ 该轮 token × 10 万。

用"持续低于"而不是"首次低于"，是因为真实曲线会非单调——我的数据里第 4 轮、第 8 轮都出现反弹
（长尾缺陷很晚才被修好）。只看首次会误判。我允许尾部有限次**孤立反弹**：反弹不能紧邻拐点，
且反弹后必须还有低值轮次，排除"刚跌破就反弹"的伪拐点。

0.1 是业务阈值：意思是"再花 10 万 token（约一次中等规模审计）连 0.1 个漏洞都修不出"，
等价于 100 万 token 才多修 1 个。我也做了阈值敏感性，0.05/0.1/0.2 都指向第 7 轮，说明不是阈值挑出来的。

### Q2：LLM 是模拟的，这个结论还有意义吗？

**答**：有意义，但要分清哪部分可信。**bandit 和 fuzzing 是真实执行的**——是不是发现漏洞由真实
bandit 报警和真实子进程 marker 决定，修复是否成功由重新扫描验证，这部分不是模拟。

模拟的只是 LLM 的输出长度和"发现/修复决策"的概率模型。我这样设计是因为环境没有外网 API key，
但我把 token 记账和判定逻辑都放在 provider 层之上，**换成真实模型只需设 `AUTOSAFE_LLM=litellm`，
分析代码一行不用改**。

所以当前数字的**绝对量级**不能当真实模型结论，但**方法和结论方向**（拐点存在、深度不如广度、
弱模型更贵）是可迁移的。README 的"诚实声明"里把这些边界写清楚了——我认为说清楚边界比藏起来更专业。

### Q3：预算分配那个贪心，近似比是多少？

**答**：这是**带前缀约束的多选择背包**——任务是 3 轮必须买了 1、2 轮才能买，NP-hard。贪心不保证最优。

理论界是 `G ≥ OPT / (d_max/d_min)`，但我的数据里有大量 0 密度轮次，所以这个界很松、没有实用价值。
我做的是**实证对比**：三种策略真实跑一遍，adaptive 46→55 修复、breadth 46、depth 33。
更有价值的发现是：**投影值与真实执行完全一致**（46/33/55），说明只要有一次基线实验的曲线，
后续预算规划可以完全离线算，不必为每个方案都真跑一遍——这对按 token 计费的真实场景是直接省钱。

我还在实现里踩了一个坑：纯贪心会跳过"首轮没修出东西"的任务，导致 8 个任务被完全放弃。
修法是先做一轮全覆盖探查再加深，收益从 35 提到 46。

### Q4：怎么保证不是过拟合？只有一个 seed 吧？

**答**：主实验确实是单 seed（seed=7），但另外做了 **9 次独立运行**（3 档模型能力 × 3 个 seed）。
结果 baseline 档三次都是第 7 轮（零方差），全部 9 次都落在第 5–8 轮。
另外阈值敏感性 0.05/0.1/0.2 也都指向第 7 轮。

更有意思的是敏感性分析暴露了一个规律：**模型越弱，拐点越晚、每修复成本越高**
（weak 均值 10 轮 / 14,276 token per fix，strong 均值 6 轮 / 6,669）。
所以"跑满 N 轮"这种固定策略**跨模型不可迁移**，换模型必须重测——这本身是个有工程价值的结论。

### Q5：这个项目的哪部分最难？或者你踩过最大的坑？

**答**：最难的不是写 Agent，是**让数字可信**。我踩过三个真实的坑：

1. **累计曲线聚合口径错了**。初版只对"还活着的任务"求和，任务提前收敛后总和会下降，
   于是出现负边际收益（-380.95），`log(负数)` 直接让外推崩溃。修正为
   "每个任务跑到 min(r, 实际轮数)，提前收敛的沿用最终值"——**已花的 token 不会退回来**，
   累计曲线必须单调不减。这个 bug 差点让整个分析结论反向。
2. **图会骗人**。fig1 里我用弧形箭头指向注释框，那条粗弧线被误读成"累计修复数骤降到 0"；
   fig2 的 symlog 轴在没有负值时也留了负数区间，把 0 值柱拉成一根尖刺，看起来像"某个极小的正数"。
   这两处都是自己 read_image 目视才发现的，最后我写了个"图表自检清单"进报告（5.1 节）。
3. **测试测错了东西**。我有一条测试断言报告里有 `figures/xxx.png` 这个字符串，
   但 REPORT.md 在项目根、图在 `results/figures/`，所以那 6 张图在 GitHub 上全是死链。
   测试检查了实现细节而不是真实效果，正好把 bug 放过去了。改成"路径必须能真正 resolve 到文件"。

## 八、一分钟口述版（面试自我介绍用）

> 我做过一个多 Agent 代码安全审计的项目。背景是这样：AutoSafeCoder 这类研究证明
> 让三个 Agent 反复迭代能减少 13% 的漏洞，但没人算过这笔账——**这些提升花了多少 token？
> 跑到第几轮之后就不划算了？**
>
> 我就搭了个实验台，用真实的 bandit 和真实的模糊测试做判定，逐轮记录 token 和修复数，
> 然后定义"每 10 万 token 修复几个漏洞"这个指标去找拐点。结果是**第 7 轮**，
> 之后每花 10 万 token 连 0.1 个漏洞都修不出来。
>
> 更有意思的是预算对比：我以为"少数任务深挖"会更划算，结果**深度迭代反而是最差的**，
> 比广度覆盖少修 28%——因为它放弃了大量任务。真正最优的是"先全覆盖一轮，再按边际收益加深"，
> 能多修 17.0%。
>
> 这个项目我最满意的不是模型，是**让数字可信**：判定不交给模型自评、图表要防止误导、
> 测试要检查真实效果而不是字符串匹配。过程中我自己找出了三个会导致结论错误的 bug。
